# 05. Серверный HUD через шрифты, отрицательные пробелы и Core Shaders (Zero-Client-Mod HUD)

## 1. Концепция Zero-Client-Mod HUD

Рендеринг кастомных двумерных интерфейсов (полосы здоровья, индикаторы патронов, ячейки счёта раундов, радары) на чистом ванильном клиенте без установки Fabric/Forge модов у игрока:
- **Канал доставки:** Пакеты заголовка BossBar (`net.kyori.adventure.bossbar.BossBar`).
- **Скрытие ванильного боссбара:** В ресурспаке текстура боссбара цвета `PINK` делается 100% прозрачной (1x1 прозрачный PNG), а прогресс устанавливается в `0.0f`.
- **Шрифтовой стек:** Шрифт с bitmap-провайдерами (`assets/<namespace>/font/hud.json`) и провайдером отрицательных пробелов (`type: "space"`).
- **Позиционирование:** Клиентский вертексный шейдер текста `rendertype_text.vsh` перехватывает глифы по аномально огромному подъёму (`ascent`) и трансформирует вершины в точные экранные координаты интерфейса.


## 2. Математика кодирования координат и слоёв в `ascent`

Ванильный движок шрифтов Minecraft рассчитывает вертикальную позицию глифа:
`pos.y = baseline - ascent`

Чтобы закодировать слой наложения (слой 0 = пустая рамка, слой 1 = заполненная победа) и экранную координату `Y` в одно число, используется 13-битный сдвиг:

### 2.1. Формула расчёта `ascent` (на сервере / в ресурспаке):
```
bits = 1024 + layer_id          // layer_id: 1 = фоновый слой, 2 = слой контента
ascent = -((bits << 13) + 4095 + layout_y + element_y)
```
- `layout_y`: базовый отступ интерфейса от верхнего края экрана (в пикселях GUI).
- `element_y`: вертикальное смещение конкретной строки/элемента.

### 2.2. Декодирование в вершинном шейдере (`rendertype_text.vsh`):
```glsl
#define HEIGHT_BIT 13
#define MAX_BIT 10
#define ADD_OFFSET 4095
#define DEFAULT_OFFSET 29

if (ProjMat[3].x == -1.0 && pos.y >= ui.y) {
    int bits = int(pos.y) >> HEIGHT_BIT;
    if (((bits >> MAX_BIT) & 1) == 1) {
        int id = bits - (1 << MAX_BIT); // восстанавливает layer_id
        
        // Боссбар центрирует заголовок, сдвигаем начало координат к левому краю
        pos.x -= 0.5 * ui.x;
        
        // Снимаем огромный сдвиг ascent, возвращая quad к точному Y на экране
        pos.y -= float((bits << HEIGHT_BIT) + ADD_OFFSET + DEFAULT_OFFSET);
        
        // Применяем Z-индекс слоя для исключения Z-fighting
        if (id == 2) {
            pos.z += 1.0;
        }
    }
}
```


## 3. Динамическое X-позиционирование отрицательными пробелами (`type: "space"`)

Вместо компиляции отдельных глифов под каждую экранную ячейку (как в устаревших подходах с генерацией 800+ провайдеров в JSON), используется **динамическое курсорное смещение**:

### 3.1. Таблица пробелов в `hud.json`:
Провайдер типа `space` регистрирует диапазон кодовых позиций (например, `0xF0000`..`0xF4000`) со значениями сдвига от `-8192` до `+8192`:
```json
{
  "type": "space",
  "advances": {
    "\U000f0000": -8192,
    "...": "...",
    "\U000f2000": 0,
    "...": "...",
    "\U000f4000": 8192
  }
}
```

### 3.2. Алгоритм отрисовки строки элементов на сервере (Java):
```java
StringBuilder sb = new StringBuilder();
int cursor = 0;

for (int s = 1; s <= count; s++) {
    int targetX = (s - 1) * BOX_STEP;
    int dx = targetX - cursor;
    
    // Вставляем отрицательный/положительный пробел до нужного X
    while (dx != 0) {
        int step = Math.max(-8192, Math.min(8192, dx));
        sb.appendCodePoint(0xF2000 + step);
        cursor += step;
        dx -= step;
    }
    
    // Добавляем глиф (ширина текстуры 11px + 1px ванильного отступа = 12px advance)
    sb.appendCodePoint(GLYPH_CHAR);
    cursor += 12;
}

// В конце сбрасываем суммарный сдвиг в 0, чтобы строка не смещала центр боссбара
int dx = -cursor;
while (dx != 0) {
    int step = Math.max(-8192, Math.min(8192, dx));
    sb.appendCodePoint(0xF2000 + step);
    cursor += step;
    dx -= step;
}
```

> [!TIP]
> **Zero Allocation & Reusability:** При таком подходе достаточно объявить ровно **1 глиф на текстуру строки** вместо сотен уникальных символов для каждой ячейки.


## 4. Динамическое масштабирование строк (Dynamic Row Stacking)

Если в игре участвует переменное количество команд/линий (например, дуэль 2 команд, либо матч на 4 команды):
- **Проблема статических привязок:** Если цвет жестко привязан к конкретному `ascent`, отключение пустых команд оставит черные дыры в 24-36 пикселей между строками.
- **Решение:** В шрифте создается матрица $L \times C$ (`линия 0..3 × цвет команды`):
  - Линия 0: `ascent = -8400907` (empty), `-8409099` (win).
  - Линия 1: `ascent = -8400919` (empty), `-8409111` (win).
  - Линия 2: `ascent = -8400931` (empty), `-8409123` (win).
  - Линия 3: `ascent = -8400943` (empty), `-8409135` (win).
Сервер фильтрует только активные команды (`activeTeams`) и компактно укладывает их на экранные линии `0..N-1` сверху вниз без визуальных пропусков.


## 5. Устранение тени шрифта в Paper 1.21.4+

Ванильный Minecraft по умолчанию рендерит темную тень под каждым глифом текста, что создает грязный ореол вокруг пиксель-арта интерфейса.

В Paper 1.21.4+ добавлен `ShadowColor`, отключающий тень:
```java
try {
    Class<?> scClass = Class.forName("net.kyori.adventure.text.format.ShadowColor");
    Method noneMethod = scClass.getMethod("none");
    Object none = noneMethod.invoke(null);
    Method shadowColorMethod = builder.getClass().getMethod("shadowColor", scClass);
    shadowColorMethod.invoke(builder, none);
} catch (Throwable ignored) {
    // На старых версиях Paper/Spigot вызов безопасно пропускается
}
```
