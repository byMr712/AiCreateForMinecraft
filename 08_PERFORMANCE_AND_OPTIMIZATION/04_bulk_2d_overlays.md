# 04. Массовая 2D-отрисовка: один оверлей вместо тысяч draw-call'ов

> Практика на карте с районами: 300 полигонов давали 129 мс на кадр, 1000 — 1.5 с. После переделки — 0.01 мс на кадр при том же виде. Здесь общий приём, применимый к любым «много заливок/линий в GUI».

## 1. Симптом и диагноз

Районы рисовались сканлайн-заливкой: на каждый район перебор всех точек для каждой экранной строки + `g.fill` на каждый отрезок + `Paper.line` на каждое ребро. Профилирование по частям дало неожиданное:

| Что | 300 районов | 500 | 1000 |
| :--- | ---: | ---: | ---: |
| точек после упрощения | 5 816 | 9 695 | 18 766 |
| время в `drawRegions` **до** | 129 мс | 420 мс | 1539 мс |
| время в `drawRegions` **после** | 0.009 мс | 0.004 мс | 0.026 мс |
| «запекание» слоя | 11 мс | 7 мс | 11 мс |

Обратите внимание: после упрощения на район оставалось ~19 точек, а кадр всё равно стоил сотни миллисекунд. Значит дело **не в математике полигонов, а в количестве вызовов отрисовки**. В этом GUI-API один `g.fill`/`blit` с матричными преобразованиями стоит микросекунды, и 10–30 тысяч вызовов на кадр — это секунды.

Вывод: оптимизировать надо не цикл, а **число draw-call'ов**.

## 2. Решение: CPU-растеризация в одну текстуру

Слой районов растеризуется в `int[]` (ARGB) размером с область карты, загружается в `DynamicTexture`, и рисуется **одним** `blit` за кадр. Пересчёт — только когда меняется вид или данные.

```java
long key = regionKey(regions, dim, selectedId);   // cx, cz, zoom, размер, id+pts+цвет каждого района
if (key != regionCacheKey) {
    int[] pixels = overlay.begin(w, h);            // очистка + (пере)создание текстуры
    rasterize(pixels, regions, dim, selectedId);   // заливки + обводки в пиксели
    regionCacheKey = key;
}
overlay.draw(g, x, y);                             // upload (если был пересчёт) + один blit
```

Ключ кэша обязан включать всё, что влияет на картинку:

- `cx`, `cz`, `zoom`, `x`, `y`, `w`, `h`;
- `selectedId` (выделенный район рисуется золотым и толще);
- для каждого района: `id`, **identity массива `pts`** (`System.identityHashCode(r.pts)` — правки заменяют массив), `hidden`, `filled`, `color`.

## 3. Что ещё обязательно (иначе не взлетит)

1. **Отсечение по мировому bbox до построения точек.** Хранить `minX/maxX/minZ/maxZ` в самом районе, пересчитывать лениво при замене `pts`; район вне экрана не должен даже трансформировать вершины.
2. **Упрощение контура в экранных координатах** (RDP, допуск ~0.75 px). На 2000 точках свободного рисования при текущем зуме остаётся 50–150; картинка не меняется, потому что всё мельче пикселя.
3. **Заливка в пиксели с ручным alpha-blending** (`src over`) — полупрозрачные районы должны складываться как раньше.
4. **Обводка растеризуется линиями Брезенхема** (толщина 1–3 px), а не `Paper.line` на каждое ребро.
5. **Подписи — отдельный проход и только для районов, где имя помещается** (`maxX - minX >= 24`). Иначе на 1000 мелких районов вы получите 1000 текстовых draw-call'ов и нечитаемую кашу.
6. **Скретч-буферы** под точки/пересечения/стек RDP: без аллокаций на каждый район и кадр.
7. **Пиксели грузить только после пересчёта** (флаг `dirty`), иначе 230k вызовов `setPixel` каждый кадр.

## 4. Подводные камни версий

| Что | 1.21–1.21.1 | 1.21.2+ | 1.21.6+ / 26.x |
| :--- | :--- | :--- | :--- |
| запись пикселя | `setPixelRGBA` (**ABGR** + `swap`) | `setPixel` (ARGB) | `setPixel` |
| `DynamicTexture` | `new DynamicTexture(image)` | `new DynamicTexture(image)` (1.21.5 уже supplier) | `new DynamicTexture(() -> "name", image)` |
| `blit` | `g.blit(id, x, y, 0f, 0f, w, h, w, h)` | `g.blit(RenderType::guiTextured, id, ...)` | `g.blit(RenderPipelines.GUI_TEXTURED, id, ...)` |
| тип id | `ResourceLocation` | `ResourceLocation` | `Identifier` (с 1.21.11) |

**Важно про альфу:** на 1.21–1.21.5 простой `g.blit(id, ...)` **не включает blending сам** (в отличие от перегрузки с цветом) — он рисует с тем состоянием, которое осталось после предыдущих вызовов. Если перед этим рисовались тайлы/иконки без `enableBlend`, полупрозрачный оверлей станет **непрозрачным**. Лечится явно:

```java
RenderSystem.enableBlend();
RenderSystem.defaultBlendFunc();
g.blit(id, x, y, 0f, 0f, width, height, width, height);
```

На 1.21.6+/26.x смешивание задаёт сам пайплайн (`RenderPipelines.GUI_TEXTURED` / `RenderType.guiTextured`), там ничего добавлять не нужно. Симптом на глаз: «районы/полупрозрачные заливки стали плотными» на старых ветках и нормально на новых.

Поэтому `RegionOverlay` — маленький класс, который генерируется/адаптируется скриптом переноса по содержимому `MapTile` ветки (там уже есть все нужные варианты).

## 5. Цена «запекания» и когда её прятать

Пересчёт слоя на 640×360 — это ~230k `setPixel` + upload, в софтверном рендерере ~7–12 мс. Это заметно только при панорамировании/зуме (каждый кадр меняется ключ). Варианты, если станет мало:

- грузить только изменившийся прямоугольник (`NativeImage` + `upload` части не поддерживает напрямую — нужен dirty-rect и загрузка подрегиона);
- во время перетаскивания рисовать «упрощённый» слой (например, только обводки) и запекать после остановки;
- держать две текстуры и обновлять асинхронно.

## 6. Как мерить

Добавить в `MapView` две публичные статические метрики (обновляются двумя `nanoTime()` на кадр):

```java
public static long lastRegionsNanos;   // полное время drawRegions
public static long lastBakeNanos;      // время последнего пересчёта
public static int lastRegionsDrawn;    // сколько районов попало в слой
public static int lastRegionsPoints;   // сколько точек после упрощения
```

Gametest: создать N районов по M точек, открыть карту, подождать 10 тиков и прочитать метрики. Проверять **и** «холодный» кадр (bake), **и** установившийся (perFrame) — иначе легко обмануть себя кэшем.

Готовый стресс-тест с этими метриками — `RegionPerfTest` из [09/08_client_gametest_suite.md](../09_CROSS_VERSION_MIGRATION_AND_PORTING/08_client_gametest_suite.md), §6.8.

## 7. Чек-лист

- [ ] Число draw-call'ов на кадр не зависит от количества объектов.
- [ ] Ключ кэша включает вид, выделение и identity/цвет каждого объекта.
- [ ] Отсечение по bbox стоит до трансформации вершин.
- [ ] Упрощение делается в экранных координатах, а не в мировых.
- [ ] Пиксели грузятся только после пересчёта.
- [ ] Подписи не рисуются там, где физически не помещаются.
- [ ] Для старых веток учтены ABGR и сигнатуры `blit`.
